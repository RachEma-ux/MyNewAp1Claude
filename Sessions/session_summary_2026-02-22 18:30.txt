## Architecture: Governance Layer
```
Server Startup → initializeGovernance() → Validates startup conditions + architecture
                                         → Logs findings, sets strict/permissive mode

API Request → tRPC middleware → protectedProcedure/adminProcedure (existing RBAC)
            → Policy Gate (enhanced) → RBAC permission check → Allow/Deny
            → Governance Router → Self-check, publication gate, lifecycle guard, metrics

Lifecycle Transition → Lifecycle Guard → Stage validation → Audit log → Allow/Block
Publication Request → Publication Gate → Triple validation → Risk report → Allow/Block

CI/CD → governance-gate.yml → Secret scan + Eval detection + Architecture check + Docs check
```

## Key Design Decisions
- Governance engine runs in strict mode (fail-closed) in production, permissive (fail-open) in development
- Policy gate upgraded from default-allow to RBAC-checked — backward compatible (unmapped actions still pass through)
- Separation of duty: submitter cannot validate or publish their own entry
- 6 governance roles extend the existing admin/user model without breaking backward compatibility
- Self-check endpoint provides monitoring-ready compliance report with recommendations
